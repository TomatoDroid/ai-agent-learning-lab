## 拆解

### 一条公式，三种说法

<div class="anim" data-anim="formula">▶ 动画“一条公式的三种说法”需要在课程网站中观看。</div>

三个层次说的是同一个东西：

| 直觉 | 实现 | 学术 |
| --- | --- | --- |
| 大脑 | LLM | 策略（Policy） |
| 眼睛 | 上下文 | 观察与历史 |
| 手脚 | 工具 | 观察/行动接口 |

两个容易忽略的细节：

- **“眼睛”只是粗略的类比。** 上下文里不仅有环境信息和对话历史，还有工具定义。也就是说，Agent “看到”的东西里包括“我有哪些手脚可用”。
- **公式不包含环境。** 文件、网页、数据库、用户、其他 Agent 都是环境。Agent 只能通过观察和行动与它们交互。这条边界在第一章会反复用到。

### 两大部分

| 部分 | 章节 | 回答的问题 |
| --- | --- | --- |
| 构建 | 第 1–6 章 | 如何构建 Agent：概念、上下文、记忆与知识、工具、Coding Agent、交互 |
| 提升 | 第 7–10 章 | 如何让它变强：先用**评估**建立可度量的反馈，再从**模型参数**（后训练）、**单体系统**（持续进化）、**群体系统**（多 Agent）三个层面扩展能力 |

注意第二部分的顺序：评估在最前面。没有评估，就分不清提升是来自设计还是来自随机波动。

### 五个贯穿全书的设计模式

| 模式 | 一句话 | 第一次出现 |
| --- | --- | --- |
| 提议者–审核者 | 产出和评判由两个不共享上下文的角色承担，因为自审不可靠 | 第三、四、五章 |
| 渐进式披露 | 先给目录，按需加载细节 | 第二章 Skills |
| 只增不改 | 状态以追加方式演进，可缓存、可重放、可审计 | 第二章 KV Cache |
| 边界集 + 保留集 | 任何修改都要在“该变的”和“不该变的”两批样本上验证 | 第七章 |
| 最小 diff + 可回滚 | 每次改得尽量小、带来源、能单独回滚 | 第三、五、九章 |

## 动手

1. 拿一张纸（或新建一个文件），画出你自己的全书地图：中间写公式，向外画出十章，每章旁边写一句“它解决什么问题”。先凭引言里的章节介绍写，学完每个模块再回来修改。
2. 选一个你常用的 AI 产品（Cursor、豆包、ChatGPT……），用“眼睛 / 手脚 / 策略”三栏各写一行。第一章 1.1 课会回来检查这份分析。

## 检验（先闭卷回答，再展开）

<details>
<summary>1. “实践在前，命名在后”的三个例子是什么？</summary>

在 Skill 概念流行之前，用动态加载提示词解决提示词膨胀，用命令行工具解决工具列表膨胀，用系统状态栏让 Agent 感知环境和时间；在 harness 概念流行之前，就用类似 Claude Code 的方法解决工具调用不稳定、幻觉、越权和不遵循指令；在 loop engineering 流行之前，就用“提议者–审核者”解决模型过早认为任务完成。
</details>

<details>
<summary>2. 为什么作者把“建立评估机制”列为两个关键条件之一？</summary>

没有评估，就无法判断一次改动的提升来自设计本身还是随机波动。评估把迭代从经验判断变成可比较、可复现的工程过程。
</details>

<details>
<summary>3. Environment 属于 Agent 吗？</summary>

不属于。公式只描述 Agent 边界之内的实现。环境（文件、数据库、网页、用户、其他 Agent、物理或仿真世界）在外面，Agent 只能通过观察和行动接口与它交互。即使仿真环境和 Agent 跑在同一个进程里，它也仍然是环境。
</details>

<details>
<summary>4. 为什么第二部分从评估开始，而不是从后训练开始？</summary>

评估提供可度量的反馈信号，是后训练、持续进化、多 Agent 改进的共同前提。先有尺子，才能知道哪种改进有效。
</details>

## 复盘卡

> **原则**：Agent = LLM + 上下文 + 工具；生产形态是 Model + Harness。
> **边界**：公式不包含环境；Harness 不是“模型之外的一切”，而是 Agent 边界内、模型之外的那一层。
