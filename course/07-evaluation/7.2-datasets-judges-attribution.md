## 拆解

### 好的评估集是修出来的

公开基准的设计手法比它的分数更值得借鉴：

| 问题 | 基准的做法 |
| --- | --- |
| Agent 说“完成了”其实没完成 | 验证器只核实机器可复核的事实：SWE-bench 要求修复前失败、修复后通过（FAIL_TO_PASS），原本通过的仍然通过（PASS_TO_PASS）；OSWorld 直接连数据库、读 DOM 和 cookie |
| 模型变强后评估集很快过时 | 分难度：GAIA 三级（人类 93.9/91.8/87.3%，GPT-4 30.3/9.7/0%），每级失败指向不同的改进方向 |
| 题目被训练数据背下来 | GAIA 要组合多个信息源并配专门制作的附件；AndroidWorld 用参数化模板每次随机实例化；Terminal-Bench 嵌入 canary GUID，让泄漏**可被检测** |
| 题目本身有问题 | 人工筛选和持续修补：SWE-bench Verified 从 1699 个人工检查的任务里只留下 500 个；OSWorld 发布后 15 个月修了 300 多个问题 |

自建评估集有三个来源：**公开基准**用来粗筛模型、借鉴手法；**自建业务集**覆盖真实任务分布，是选型和 Harness 决策的依据；**生产轨迹回流**（用户纠正、点踩、事后审计发现的问题）成本最高也最准。系统上线一段时间后，回流用例会成为主体。

### Rubric 与 LLM-as-a-Judge

<div class="anim" data-anim="judge-pipeline">▶ 动画“Rubric 评判：分档、加权、一票否决”需要在课程网站中观看。</div>

验证方式是一条谱系：能写成程序断言的继续用断言（便宜、稳定、可进 CI），只有“回复得不得体”“有没有弄错人物关系”这类无法机械判定的维度，才交给 Rubric 加评判模型。

Rubric 四准则（Scale AI）：

1. **基于专家指导**：反映领域知识，不只是语言流畅度；
2. **全面覆盖**：正面标准之外，还要列出陷阱（高风险的常见错误）；
3. **按重要性加权**：必要项、重要项、可选项，外加**一票否决**。幻觉就是典型的否决维度，它也能防止关键词堆砌式的奖励作弊；
4. **评价标准自包含**：每一档写成可验证的具体行为（“准确回答 Dr. Chen”），不写“展示了深刻理解”。

评判模型最典型的偏见是**长度偏差**。三种防范：Rubric 里显式惩罚冗长或规定长度上限；配对比较前把两个候选的长度控制到相近；定期审计评分与长度的相关性。

表 7-3 是一个好例子：三种记忆系统在 60 个问题上，JSON Cards 68.3%、RAG 48.3%、混合 66.7%。**混合方案没有自然胜出**；180 次评判里幻觉否决触发了 28 次。

### 配对比较与 Elo

<div class="anim" data-anim="pairwise-elo">▶ 动画“配对比较：交换位置判两次，再用 Elo 排名”需要在课程网站中观看。</div>

不定义绝对分数，只问“A 和 B 哪个更好”。评判由 LLM 完成时要防**位置偏差**：交换顺序各判一次，两次一致才算数，矛盾记为平局或送人工复核。

Elo 是 Bradley-Terry 模型的在线更新形式：分差 200 时强者期望胜率约 76%；爆冷带来更大的分数调整。它受 K 和**比赛顺序**影响，而 BT 极大似然一次性拟合全部对局，与顺序无关。

### 失败归因：找第一个错误

<div class="anim" data-anim="failure-attribution">▶ 动画“失败归因：找到第一个错误，再找根因”需要在课程网站中观看。</div>

端到端评估只说“失败”。要让结果驱动修复，每条失败轨迹都要标出：**主要错误类别、第一个不可接受行为的步骤、对应的调用或输出、可复核的证据**。后续错误往往只是连锁反应。

几条要点：

- 归因记录要**结构化**（JSON/YAML），引用步骤号、工具名和观察证据，区分根因与后果，给出置信度。`old_string` 匹配失败后连续重试三次，是一个根因加三个后果，不是四个根因。
- **规则先筛，LLM 再定位**：完成声明与真实执行过的命令交叉核对、diff 是否触及测试断言和 skip、是否改了公开 API 而没有迁移，这些都能先用规则找出嫌疑轨迹。
- **“做对了但说错了”**容易被整体成功率掩盖：τ²-bench 基线里有信息告知要求的 704 次运行失败 240 次，其中 80 次环境状态完全正确，只是告诉用户的信息错了。
- **根因归属决定改什么**：AndroidWorld 记账的例子里，T3A 是纯文本 Agent，观察里根本没有图像像素。记成“模型不会 OCR”，下一步就会去换模型；真正该做的是补观察通道。

失败归因往往反映的是**产品问题**，不只是技术问题，所以可以借助 LLM，但不能完全依赖 LLM。

### 端到端回归与前缀回归

<div class="anim" data-anim="prefix-regression">▶ 动画“轨迹前缀回归：冻结上下文，只看下一步”需要在课程网站中观看。</div>

| | 端到端回归 | 轨迹前缀回归 |
| --- | --- | --- |
| 从哪开始 | 初始状态和用户请求 | 首个错误之前冻结的上下文、对话、工具返回和环境状态 |
| 检查什么 | 最终状态、必要输出、安全条件 | 下一步（或几步）动作是否落在**可接受动作集合**里，是否触发禁止动作 |
| 优点 | 最接近生产 | 便宜、确定，能隔离单个策略或工具问题 |
| 缺点 | 说不清坏在哪一步 | 只验证一个决策边界 |

答案是一个**集合**，不是唯一动作：“先读仓库规则”“先问用户”“拒绝危险操作”都可以是可接受的。实验 7-7 说明了为什么要看具体用例：同一组记忆用三种写法表示，总成绩都是 6/11，失败位置却不同，三种都没过的三个用例才是该修的应用策略。

| 测试 | 想让你看到 |
| --- | --- |

## 检验（先闭卷回答，再展开）

<details>
<summary>1. SWE-bench Verified 为什么要两组测试同时检查？</summary>

FAIL_TO_PASS 证明问题确实解决了，PASS_TO_PASS 证明没有引入新缺陷。只检查前者，Agent 可以删改妨碍通过的断言蒙混；只检查后者等于没检查。两组同时检查，“已修复”和“未破坏”才各自可证。
</details>

<details>
<summary>2. 防数据泄漏的三种办法各是什么思路？</summary>

GAIA 让答案无法从单一网页检索到：要组合多个信息源，部分题配有互联网上不存在的附件。AndroidWorld 用参数化模板每次随机实例化，回放固定操作序列失效。Terminal-Bench 嵌入 canary GUID，不阻止泄漏，但能检测泄漏。
</details>

<details>
<summary>3. 一票否决为什么必要？</summary>

有些错误无论其他方面多好都不可接受，例如客服编造信息。加权平均会让它被其他维度的高分稀释；否决项让它直接归零。它也能防止关键词堆砌式的奖励作弊。
</details>

<details>
<summary>4. 怎样防范 LLM 评判的长度偏差和位置偏差？</summary>

长度偏差：Rubric 里显式惩罚冗长或规定长度上限，配对比较前控制长度相近，定期审计评分与长度的相关性。位置偏差：交换顺序各判一次，两次一致才计入，不一致记为平局或送人工复核；大样本下也可以随机化展示位置。
</details>

<details>
<summary>5. AndroidWorld 记账的例子里，首个错误在哪？根因是什么？为什么归属很重要？</summary>

首个错误在第 8 步：思考里已经承认看不到图片内容，却既没停下也没报告。根因是 Harness 的观察通道缺失（T3A 只有元素树，没有像素），不是模型不会 OCR。记成模型问题会去换模型或训练 OCR，记对了才会去补观察通道。
</details>

<details>
<summary>6. 轨迹前缀回归的答案为什么是一个集合？</summary>

同一个决策点往往有多个合理的下一步（先查状态、先提问、拒绝），只认一个会把合理的行为判错。集合之外再列出禁止动作，测的就是“这个决策边界有没有被修好”。
</details>

## 复盘卡

> **数据集**：验证器只信可复核的事实（双重验证）；分难度；防泄漏（组合信息源、参数化模板、canary）；持续修补；三个来源中生产回流最准。
> **评判**：能断言就断言；不能的用 Rubric（专家指导、全面覆盖、加权 + 否决、标准自包含）加评判模型；审计长度偏差。
> **比较**：交换位置判两次，一致才算；Elo 是 BT 的在线版，受顺序影响。
> **归因**：找第一个错误，区分根因与后果，结构化记录；规则先筛、LLM 再定位；根因归属决定改什么。
> **回归**：端到端保证不退化；前缀回归冻结上下文，检查下一步是否在可接受动作集合里。
