## 拆解

### 写系统提示词：四个维度

把系统提示词想成给一个聪明新员工的手册。**如果一个聪明的新员工读完还不知道该怎么做，Agent 也一样不知道。**

| 维度 | 要点 | 实验 2-4 的结论 |
| --- | --- | --- |
| 语气与风格 | 简洁、失败时少辩解；大写 NEVER 留给真正关键的约束，用多了会被稀释 | 换成 Trump 风格或满屏表情，完成率影响**有限** |
| 格式 | Markdown 给人看层次，XML 标签给模型精确语义（`<working_directory>` 比“当前目录：”更好懂） | — |
| 组织方式 | **流程驱动**（SOP：第几步、目标、异常怎么走），而不是上百条无序规则 | 只打乱结构，成功率**下降超过 30%**，“先验证身份再退款”被拆散后会被跳过 |
| 内容 | 业务规则细化到可执行，例如 “NEVER use percentage_based_one_time for refunds” | 去掉工具描述只留签名，工具调用错误率 **+45%** |

最后一行有一个反直觉的结论：**模型不缺风格适应能力，缺的是结构和细节。** 花一小时打磨语气，不如花一小时把规则排成流程。

### 业务规则：产品经理的工作

“根据任务情况选择合适的计费类型”这种模糊规则，会让同一任务在不同时间被分到不同类别。“帮我取消 Netflix 订阅”算不算“省钱”？“帮我退货”算不算？产品经理必须把边界写死：提成只用于**谈判降低现有账单**；“节省”只基于现有账单，避免模型把“防止明年涨价”也算成省钱。

作者的立场：**模型擅长遵循复杂指令，但不应该在业务规则制定上有太多自由裁量权。** 在优秀的 Agent 公司里，提示词通常由产品经理设计；工程师负责把规则准确编码进去，但不擅自决定业务逻辑。

### Few-shot 与工具定义：都要服从缓存

- **Few-shot**：规则说不清时（文案风格、报告格式、语气分寸）给两三个覆盖边界的示例，胜过十个大同小异的。示例处在上下文靠前的位置，所以**每类任务用一套固定示例**，不要逐请求检索。
- **工具定义**：好的描述写清使用边界、具体示例、性能提示和工具间的协作关系（第四章展开）。工具多了以后，2026 年的主流 API 已原生支持**工具搜索**：静态前缀只放名称和简述，完整 schema 在模型请求后**追加到末尾**。它只在被发现的那一轮“在末尾”，之后就固定在轨迹原位，成为普通历史。前提是模型训练时见过“工具定义出现在对话中间”。

### 提示注入：指令与数据分不清

<div class="anim" data-anim="injection">▶ 动画“间接提示注入：藏在网页里的‘指令’”需要在课程网站中观看。</div>

本质是**攻击者把伪装成指令的文本，通过 Agent 处理的外部内容混进上下文**。每一个感知工具（网页、文档、邮件，甚至图片 EXIF）都是入口；Skills 和状态栏（下一课）是新的注入面，第三方 Skill 要像审查代码一样审查。

上下文层的三种防御，都在帮模型分清“谁有权指挥我”：

| 防御 | 做法 | 局限 |
| --- | --- | --- |
| 来源标记 | `<external_content source="webpage">…</external_content>` | 攻击者会伪造闭合标签，要转义 |
| 结构化角色 | 外部数据只走 tool 角色，绝不混进 user | 依赖模型训练时建立的角色优先级 |
| 输入清洗 | 扫描“忽略之前的指令”等短语 | 换个说法就绕过，只能当辅助 |

动画最后一个场景是本课最重要的一句话：**上下文层只能降低成功率，保证来自执行层**。“把对话历史写到 /tmp”这一步，哪怕模型被骗了，1.3 课的 Guard 也会因为“往工作目录外写文件”把它拦下来等人确认。这正是第一章三层护栏在第二章的落地。

## 动手：来源标记与注入扫描

打开 `mini-agent/mini_agent/injection.py`，完成**练习 2.3**：

- `wrap_external`：给外部内容包上来源标记。两条安全要求写在文档字符串里：中和内容里伪造的 `</external_content>`；清洗 `source` 属性防止逃逸。
- `scan_injection`：返回命中的可疑模式。

```sh
python -m pytest tests/test_ch02_injection.py -v
```

注意这三个测试想让你看到的事：

| 测试 | 想让你看到 |
| --- | --- |
| `内容里伪造的闭合标签被中和` | 来源标记本身也会被攻击，标记要“防转义” |
| `换个说法就能绕过扫描_所以它只是辅助` | 输入清洗给不出保证 |
| `纵深防御_即使模型被骗_写入也要过执行层` | 剧本里的模型**真的被骗了**，去调用写文件；拦住它的是你在 1.3 写的 `assess_risk` 和默认拒绝的 `confirm` |

`Agent` 类（`agent.py`）会自动给标记了 `untrusted_output=True` 的工具（例如 `fetch_page`）的结果套上 `wrap_external`。这是“结构化角色 + 来源标记”的组合：外部数据既在 tool 角色里，又带着来源。

**再做一件事**：`mini-agent/mini_agent/agent.py` 里 `Agent` 的默认系统提示词只有一句话。按本课的“四个维度”，为 `chat` 模式（一个能读写工作目录的助手）写一份流程驱动的 SOP，用 Markdown 标题加 XML 标签组织，通过 `Agent(..., system_prompt=...)` 传进去试试。

## 检验（先闭卷回答，再展开）

<details>
<summary>1. 实验 2-4 的三个维度，各自对成功率的影响有多大？给你的启示是什么？</summary>

语气风格影响有限；打乱组织结构让成功率下降超过 30%；去掉工具描述让工具调用错误率增加 45%。启示：把精力花在结构（流程化）和细节（业务规则、工具描述）上，而不是语气。对人友好的信息组织方式，对模型同样友好。
</details>

<details>
<summary>2. 为什么“按请求检索最相关的 few-shot 示例”在生产里通常不可取？</summary>

示例位于上下文靠前的区域，逐请求替换等于每次都改写前缀，后面的缓存持续失效。生产系统通常为每类任务准备固定的示例集，保持字节级稳定。
</details>

<details>
<summary>3. 工具搜索把 schema “追加到末尾”。第 5 轮发现的工具，到第 20 轮时它在哪里？</summary>

还在第 5 轮的位置。之后的消息都追加在它后面，它成为普通历史并持续命中缓存，而不是每轮被搬到最新的末尾。
</details>

<details>
<summary>4. 来源标记为什么要转义内容中的 `&lt;/external_content&gt;`？</summary>

否则攻击者可以在内容里写一个闭合标签，让后面的文字看起来在标记之外，像是可信的上下文，从而绕过来源标记。
</details>

<details>
<summary>5. 只靠“在系统提示词里警告模型外部内容不可信”够不够？为什么？</summary>

不够。上下文层的防御（警告、标记、清洗）都只能降低攻击成功率：处在同一上下文中的模型很难判断自己是否已被注入。真正的保证要来自上下文之外：执行层的风险评级、权限控制、沙盒和人工确认，以及数据层的权限策略。
</details>

<details>
<summary>6. 把工具结果拼进 user 消息，除了上一课说的“丢思考”，还有什么安全后果？</summary>

模型依据角色区分可信指令和外部数据。外部数据混进 user 消息，就等于给了它用户的权威，亲手抹掉了模型辨别来源的依据。
</details>

## 复盘卡

> **原则**：新员工检验；流程驱动胜过规则堆砌；业务规则由产品定义，写到可执行。
> **缓存**：示例和工具定义都在前缀里，要固定；按需加载的内容追加到末尾。
> **安全**：注入的本质是指令与数据分不清；上下文层降低概率，执行层给出保证。
