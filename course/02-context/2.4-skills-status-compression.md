## 拆解

### Skills：目录常驻，正文按需

<div class="anim" data-anim="skills">▶ 动画“Skills：目录常驻，正文按需加载”需要在课程网站中观看。</div>

把所有领域规则塞进系统提示词有两个问题：浪费 token、稀释注意力。Skills 的答案是渐进式披露：

| 层 | 内容 | 何时进入上下文 |
| --- | --- | --- |
| 1 元数据 | `SKILL.md` frontmatter 里的 `name` + `description` | 一开始就在（目录） |
| 2 核心流程 | `SKILL.md` 正文 | 模型判断需要时（或用户敲 `/pptx`） |
| 3 细则 | 正文引用的子文档、脚本、模板 | 正文里说要看时 |

三个容易错的细节：

- **`description` 是路由条件，不是功能介绍。** “help with backend”什么都能触发；要写“何时用我、何时别用我”。
- **正文落在调用位置，以 user 消息追加。** Claude Code 中模型自主触发时，工具结果只是一句占位符，正文作为独立的 user 消息追加在后面。这是“动态信息追加到末尾”的又一次应用。
- **对缓存友好 ≠ 零成本**：正文第一次出现时要计算一次；好处是不必启动时加载全部正文，也不必回头改写已建立的上下文。

Skill 和工具的关系：用“少量通用工具 + 按需加载的 Skill”替代“成百个专用工具”，工具数少、前缀稳定（第四、五章展开）。写 Skill 的建议：角色与读者、三到五条带正反例的核心原则、禁止清单（写清例外）、参考资料。另外，**第三方 Skill 是注入面**，要像审查代码一样审查（上一课）。

### 状态栏：把“要数一遍”的东西提前算好

<div class="anim" data-anim="status-bar">▶ 动画“状态栏：把‘要数一遍’的东西提前算好”需要在课程网站中观看。</div>

本课最深刻的一个观点：**上下文学习更像检索而非推理。** 注意力擅长“笼子 37 里是什么猫”，不擅长“一共几只黑猫”。上下文里的东西从不会被自动数一遍、总结成结论，模型每次要用都得从原始记录现算，代价随记录量增长。

状态栏就是补上那缺失的“提炼层”：Harness **用代码**把计数、TODO、时间、工作目录等算好，以一条 `<agent_status>` 包裹的 **user 消息追加在末尾**。末尾有两个好处：离即将生成的 token 最近，注意力权重高；追加不改前缀。

实验结论值得记住：较小的开源模型加上状态栏，准确率可以接近前沿大模型；每轮的思考 token、延迟和花费降低约一个数量级，而且不再随上下文变长而增长。实验 2-9 中，TODO 让迭代数从 21 降到 15，详细错误信息让找到替代方案的成功率从 60% 升到 95%。

**两种更新方式**（这是本节最容易被忽略的工程细节）：

| 方式 | 做法 | 缓存代价 | 适合 |
| --- | --- | --- | --- |
| 每轮替换 | 删掉旧状态，在末尾追加新状态 | 旧状态之后的短后缀失效 | 状态大、更新频繁、轨迹长 |
| 持久追加 | 旧状态留在原地，只追加新状态（Claude Code 的 `<system-reminder>`） | 无 | 状态小、两次更新间新增消息多、会话长度受控 |

两条维护纪律：**状态栏用代码维护**（模型几乎无条件相信它，写错了就会被带偏，这也是投毒面）；**谨慎删除原始上下文**（状态栏是有损投影，只算了你预想会被问到的维度）。

### 压缩：为上下文做减法

<div class="anim" data-anim="compression">▶ 动画“上下文压缩 vs 子 Agent 隔离”需要在课程网站中观看。</div>

**三个动机**，第二个最容易被忽视：

1. 长度与成本：窗口装不下、越长越贵越慢；
2. **思考质量**：总结后的知识比原始形式更好用（宠物店：把“黑猫 90、白猫 10”写进去，模型直接检索）；即使窗口没满也会**上下文腐化**：装得下但找不到；
3. **上下文焦虑**：模型以为窗口快满了，就提前收尾。

**与 KV Cache 的调和**：压缩发生在两次调用之间；系统提示词和工具定义永远不动；被替换的位置之后缓存失效，所以**接近阈值时批量压缩，不要每轮都压**。若 thinking 被签名绑定在前缀上，要么整段压成一条摘要、不回传旧 thinking，要么交给服务端压缩（2.2 课检验第 5 题）。

**实验 2-10 的六种策略**：

| 策略 | 结果 |
| --- | --- |
| 无压缩 | 第 5 次迭代超过 128K，任务失败 |
| 个体摘要 / 组合摘要 | 能完成，但信息碎片化或超长截断；不懂相关性 |
| 上下文感知（带上查询和已知信息） | 7 次迭代、约 40K token，最省 |
| 带引用的上下文感知 | 有损压缩 + 无损索引（URL），可回溯 |
| 自适应窗口化（80% 阈值 + 批量 + `[COMPRESSED]` 标记） | 前期保留完整原文，灵活；总 token 较多 |

**生产级五层**（Claude Code 为参照）：工具结果预算（大输出存盘、替换一旦做出就冻结）→ 噪声直接删 → API 层微压缩 → 归档式逐轮摘要 → 全量压缩（带熔断器）。不同信息有不同保质期。

**四条原则**：信息价值不均匀；语义完整（“2024 年 5 月离开 OpenAI”不能压成“离开”）；任务相关；压缩即理解。还要让 Agent **定期把进展写进文档**，因为压缩最容易丢的是早期决策、约束的理由和失败的路径。

**隔离优于压缩**：会产生海量中间内容的子任务（大范围搜索代码库）交给子 Agent，主上下文只多两条消息。代价是子 Agent 看不到主上下文，任务描述必须自包含。

三个“装配后”的测试会用 `Agent` 把你的部件接进 1.2 写的循环，检查的都是 2.2 课的原则：

## 检验（先闭卷回答，再展开）

<details>
<summary>1. 好的 Skill `description` 和差的有什么区别？举一个例子。</summary>

好的描述是路由条件：写清何时使用、何时不使用，必要时给反例。差的是宽泛的功能介绍，例如 “help with backend”，任何后端相关工作都能触发，路由失准。例如“当用户要写或修改周报时使用；不用于日报或会议纪要”。
</details>

<details>
<summary>2. 为什么状态栏放在末尾、用 user 角色，而不是写进 system？</summary>

写进 system 会改动前缀，破坏全部缓存。放在末尾既是追加（不影响已缓存的前缀），又离即将生成的 token 最近，获得更高的注意力权重。user 角色只是借用的消息槽位，内容来自框架，用 `<agent_status>` 标签与真正的用户输入区分。
</details>

<details>
<summary>3. 用“检索而非推理”解释：为什么状态栏能让小模型接近大模型？</summary>

“打了几次电话”这类结论不存在于上下文中，需要遍历原始记录现算，这是推理，小模型容易数错。状态栏把结论用代码提前算好写进上下文，问题变成检索，这是注意力的强项，小模型也能做好；思考 token 也不再随上下文增长。
</details>

<details>
<summary>4. 状态 200 token、每轮新增 3000 token、更新 20 次、α = 0.1，选哪种更新方式？</summary>

比较 αSN/2 = 0.1 × 200 × 20 / 2 = 200 与 (1−α)R = 0.9 × 3000 = 2700。前者小，倾向持久追加。直觉上：状态很小、两次更新间新增消息很多时，保留旧状态比反复重算长后缀便宜。
</details>

<details>
<summary>5. 为什么推荐“接近阈值时批量压缩”，而不是每轮压缩新来的工具结果？</summary>

每次替换历史中的内容，替换点之后的缓存都会失效。每轮压缩就每轮破坏缓存；在接近阈值时一次压完，只付一次缓存重建的代价。前期还能保留完整原文。`[COMPRESSED]` 标记防止重复压缩。
</details>

<details>
<summary>6. 上下文腐化和上下文溢出有什么不同？哪个更危险？</summary>

溢出是装不下，任务直接失败，容易发现；腐化是装得下但找不到，注意力被无关内容稀释，Agent 表面正常但决策质量悄悄下降，更隐蔽。
</details>

<details>
<summary>7. “在代码库中找支付回调函数”：压缩还是隔离？</summary>

隔离。交给子 Agent 去搜，主上下文只增加任务描述和结论两条消息，数万 token 的中间内容随子 Agent 丢弃，主 Agent 的前缀也不受影响。压缩是有损的、需要额外调用的事后补救。前提是任务描述要自包含。
</details>

## 复盘卡

> **原则**：上下文学习是检索而非推理；结论要提前算好放进去，而不是让模型每次现算。
> **三件工具**：Skills 让知识按需进来；状态栏把隐式状态变成显式结论；压缩和隔离让无用的东西出去。
> **一条底线**：这三件事都遵守 2.2 课的规则：前缀不动，变化追加到末尾，必须改写时批量改。
