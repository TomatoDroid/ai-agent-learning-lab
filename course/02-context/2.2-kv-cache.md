## 拆解

### 三条核心结论（必须背下来）

1. **系统提示词和工具定义一旦确定就不要改。** 哪怕多一个空格，首个不同 token 及其后的缓存都无法复用。
2. **动态信息永远追加到末尾。** 时间戳、用户状态等作为新消息追加，而不是修改已有内容。
3. **使用标准 API 格式，不要自行拼接消息。**（上一课的主题。）

### 从注意力到 KV Cache

<div class="anim" data-anim="attention">▶ 动画“注意力：Query 找 Key，按权重取 Value”需要在课程网站中观看。</div>

关键推理链：

- 每个新 token 的 Query 要和前面**所有** token 的 Key 匹配，再对所有 Value 加权求和。
- 因果注意力决定了：一个 token 在每一层的 K、V **只依赖它自己和它之前的 token**。
- 所以前面的 K、V 可以缓存复用；而如果第 k 个 token 变了，从 k 开始往后的表示会**逐层**受影响，缓存只能保留到首个不同 token 之前。
- 反过来，**在末尾追加**内容不会改变任何已缓存 token 的 K、V。这就是“追加友好、改写昂贵”的根源。

实验 2-2 里还有两个对上下文设计很有用的现象：**注意力储存池**（第一个 token 吸收大量“无处安放”的权重，这是 softmax 的数学结果）和**位置偏好**（开头和结尾获得更多注意力，中间容易被忽视，即 Lost in the Middle）。后者是 2.4 课把状态栏放在末尾的依据之一。

### 哪些写法会让缓存失效

<div class="anim" data-anim="kv-cache">▶ 动画“KV Cache：哪些 token 能复用？”需要在课程网站中观看。</div>

逐个切换场景，看统计数字。实验 2-3 的五种错误模式：

| 错误模式 | 为什么有害 | 正确做法 |
| --- | --- | --- |
| 动态系统提示词（写时间戳） | 时间戳之后全部失效 | 时间作为消息追加到末尾，或用工具获取 |
| 动态用户配置（余额、剩余次数） | 同上 | 需要时通过状态管理机制或工具获取 |
| 工具按频率动态排序 | 从第一个变动的工具起全部失效 | 固定顺序（对选工具能力几乎没影响） |
| 滑动窗口 | 破坏前缀；**丢失关键工具结果**，Agent 反复执行相同调用 | 见思考题 1 |
| 文本格式化拼接 | 偏离训练格式，削弱多步思考 | 标准 API 格式 |

### 两个层级、一个架构约束

- **KV Cache**：模型内部机制，加速一次请求内的逐 token 生成。
- **Prompt Cache**：服务端跨请求复用相同前缀的 KV Cache。缓存读取的价格通常约为首次计算的十分之一（各家不同，查文档）。

当缓存的经济效益足够大时，它会**反过来主导架构**。Claude Code 的例子：提示词用缓存边界分成两段，动态元素全部放在边界之后（N 个二值条件放在边界前会产生 2^N 种缓存键）；子 Agent 若继承父上下文就必须字节级对齐；大型工具输出的替换字符串首次出现就冻结。

更进一步，Anthropic 的“保留思考”机制用签名把每个 thinking block 绑定到它产生时的前缀上：前缀一改，后面的 thinking 全部失效。**“只追加、不改写”从性能建议变成了正确性要求。** 解法还是同一条：变化追加到末尾。

## 检验（先闭卷回答，再展开）

<details>
<summary>1. 解释为什么“改动越靠前，代价越大”。</summary>

缓存只能保留到首个不同 token 之前，之后的 K、V 都要重算（多层 Transformer 中，变化会逐层向后传播）。改动越靠前，需要重算和计费的 token 越多。
</details>

<details>
<summary>2. 为什么在末尾追加工具 schema（按需加载工具）不会破坏缓存？</summary>

因果注意力下，每个 token 的 K、V 只依赖它自己和之前的 token，与后面的 token 无关。所以在末尾追加不会改变任何已缓存 token 的 K、V；新增的 schema 只在首次出现时计算一次，此后并入前缀持续命中。
</details>

<details>
<summary>3. 滑动窗口有哪两个问题？</summary>

一是丢掉最早的消息后，后面所有消息的位置都变了，前缀不一致，缓存失效；二是可能丢掉关键的工具结果，Agent 会忘记已经拿到的信息，反复执行相同的工具调用。
</details>

<details>
<summary>4. KV Cache 省掉的是什么？没省掉的是什么？</summary>

省掉的是历史 token 的 K、V 重新投影计算，使每步解码不必重算整个前缀。没省掉的是：每个新 token 的注意力仍要遍历全部缓存的 K、V，计算量随上下文长度线性增长。这也是长上下文解码变慢、KV Cache 的显存和带宽成为瓶颈的原因。
</details>

<details>
<summary>5. 当前缀被签名绑定到 thinking 上时，“压缩旧轮次、原样保留最近几轮”为什么会出问题？</summary>

保留下来的几轮 thinking 产生时，前面是原始历史而不是摘要。前缀变了，它们会全部失效。推荐做法是把整段会话压成一条摘要、不再回传旧 thinking，或交给服务端做压缩（服务端的改动不算修改前缀）。
</details>

## 复盘卡

> **原则**：前缀不要改；动态信息追加到末尾；用标准 API 格式。
> **机制**：因果注意力 → 每个 token 的 K、V 只依赖它之前的内容 → 追加便宜，改写昂贵。
> **升级**：缓存经济性是前置的架构约束；当推理被绑定在前缀上，只追加就成了正确性要求。
