## 拆解

### 六个方向，由内向外

| 方向 | 作用对象 | 一句话 |
| --- | --- | --- |
| 思考工具 | 思维本身 | LLM 形式化，代码精确求解 |
| 业务规则约束 | 业务规则 | 关键操作前的确定性守门员 |
| 多媒体生成 | 内容呈现 | PPT、视频、3D 零件都是代码 |
| 系统适配器 | 系统接口 | 哪里接不上，就现场写一段胶水 |
| 生成式 UI | 用户界面 | 表单、图表、整个应用 |
| Agent 自举 | Agent 自身 | 用代码修复和创造 Agent |

### 代码作为思考工具

<div class="anim" data-anim="code-as-thinking">▶ 动画“代码作为思考工具”需要在课程网站中观看。</div>

模型的思考是概率性的、近似的，而数学和逻辑要求确定的、精确的答案。分工：**LLM 负责理解问题、写成形式化的代码，求解器负责算**。这和 Wolfram 的洞察一样：符号计算系统算得准但听不懂人话，LLM 恰好相反。

但要记住两个限定：求解器只保证**形式化之后**的解，翻译这一步照样会错；**模型越强，脚手架可以越薄**。评估一项 Agent 技术时，先问清楚配的是什么模型。

### 代码作为业务规则的守门员

<div class="anim" data-anim="rule-gatekeeper">▶ 动画“规则写进工具：参数是 checklist，真值才是守门员”需要在课程网站中观看。</div>

| 保障 | 放在哪 | 作用 |
| --- | --- | --- |
| ① 自然语言规则 | 系统提示词 | 向用户解释政策、寻找变通方案（“改签而非取消”） |
| ② 参数作为 checklist | 工具描述与 `expected_*` 参数 | 为了填参数，模型必须先查订单、逐条核对，常常在调用前就发现不行 |
| ③ 服务端真值校验 | 工具内部 | 舱位、保险、时间一律从数据库和服务端时钟取，不采信模型自报 |

前两重减少错误的发生，第三重确保错误不会变成**不可逆的损失**。如果把 `has_insurance` 乃至 `current_time` 设计成模型填写的参数，模型只要报错（或被诱导报错）一个值，守门员就形同虚设。**最后一道防线必须建立在模型无法伪造的数据之上**：独立性不仅指独立的模型，更指独立的数据来源。

自报值与真值不一致时要记一条审计：它能暴露模型的错误认知，也能暴露潜在的注入。

### 多媒体：提议者-审核者，以及该不该用代码

Agent 写完 Slidev 代码并不知道渲染出来什么样。所以拆成两个 Agent：**提议者**写代码，**审核者**把每页渲染成图、用视觉模型检查，给出结构化建议（页码、问题类型、严重程度）。为什么不是一个 Agent 自己看？核心是**上下文管理**：审核者每次只看最新一版的图，提议者只累积文字反馈；单 Agent 要在一个上下文里堆几十页图片的多轮迭代，很快超限。终止条件有两个：审核者判定达标，或者达到最大轮数。

代码生成还是生成模型？**一看产物有没有紧凑的精确描述**（法兰盘五六个参数就定义完了，一盆绿植没有）；**二看精度要求和可验证性**（零件尺寸可以程序化逐项核对）。还要看可编辑性：“M5 改 M6”，代码路线改一个数，生成模型只能整个重来。

### 生成式 UI：只能点菜单上的菜

<div class="anim" data-anim="generative-ui">▶ 动画“生成式 UI：一次填完，只用菜单上的组件”需要在课程网站中观看。</div>

| 做法 | 适合 | 风险与对策 |
| --- | --- | --- |
| 声明式（A2UI 类） | 表单、表格、卡片等标准交互 | Agent 只输出界面描述 JSON，客户端用受信任的组件目录渲染 |
| 直接生成代码 | 高度定制的可视化、游戏 | 提示注入可能产生恶意脚本，效果类似 XSS；要在沙盒里展示 |
| Artifact（SQL + 可视化代码） | 大量数据的查询与呈现 | 数据从数据库直达界面，不经 LLM 抄写；只读账号、只允许经过批准的 SELECT、服务端参数绑定、限时限行 |

注意区分 **A2UI**（界面描述语言）和 **AG-UI**（把 Agent 的状态流式推送到前端的事件协议），二者互补，不是同类。

**动态生成软件**改变了安全前提：业务代码随时被 Agent 重写，写在应用层的权限检查就不再可靠。目标不是“保证 AI 每次都把权限检查写对”，而是**即使 AI 写错了代码，权限约束也无法被绕过**：把信任边界下移到数据层（行级安全、受控视图、由受信任运行时绑定的访问上下文），并且所有数据访问都必须经过这一层。这和上面“服务端真值”是同一个思想，只是从一个工具推广到了整个应用。

### 代码创造代码

OpenClaw `doctor` 的两层值得注意：**先用确定性检查**覆盖过期 token、锁文件、端口冲突这些高频问题，**再让 LLM 兜底**长尾疑难；安全的修复自动执行，有风险的要用户确认。不要夸大 Agent 在其中的作用。

让 Agent 写 Agent，最有效的不是在提示词里穷尽规则，而是**给一份高质量的实现作为范例**，让它复制再修改。你手上的 mini-agent 就可以是这样一份范例。

<details>
<summary>原书的正式实验结果</summary>

- 实验 5-3：代码辅助 53.3%，纯思维链 36.7%，但差异未达显著（p=0.125）。
- 实验 5-4：每条代码轨迹都调用了约束求解器，准确率却是 39.3%，低于纯思考的 75.0%，方向与预期相反。原书保留了这个负结论：求解器只保证形式化模型的解，前提是条件被正确翻译。

## 检验（先闭卷回答，再展开）

<details>
<summary>1. 什么是元能力？为什么说代码是元能力？</summary>

元能力是“能创造其他能力”的能力。代码精确、可执行、可组合，Agent 能用它当场写出新工具（脚本、API 调用序列）、新约束（断言、校验规则）和新的表达形式（表单、PPT、视频帧），而不必事先把所有能力都预制好。
</details>

<details>
<summary>2. 取消订单工具里的 expected_* 参数有什么用？为什么服务端不采信？</summary>

它们是一张强制 checklist：为了填好它们，模型必须先查订单、逐条核对政策，常常在准备调用时就发现不能取消，转而给出替代方案。但它们只是模型的自我陈述，模型可能幻觉，也可能被注入，所以服务端一律从数据库和服务端时钟取政策事实，自报值只用于比对和审计。
</details>

<details>
<summary>3. PPT 生成为什么用两个 Agent？终止条件是什么？</summary>

核心是上下文管理：审核者每次只处理最新版本的渲染图，不受历史版本干扰；提议者只累积结构化的文字反馈。单 Agent 要在一个上下文里累积几十页渲染图的多轮迭代，很快超限。终止条件：审核者判定质量达标，或达到最大迭代轮数。
</details>

<details>
<summary>4. 什么时候该用代码生成，什么时候用生成模型？</summary>

一看产物有没有紧凑的精确描述（工业零件几个参数就能无损表达，绿植、人脸的内在复杂度近乎无限）；二看精度要求和可验证性（零件尺寸是硬约束，可以程序化核对）。另外代码路线可编辑：改一个参数重跑，其余尺寸不变。两条路也可以混用：几何体用代码，表面纹理用生成模型。
</details>

<details>
<summary>5. A2UI 类协议怎样防止生成的界面变成攻击载体？</summary>

Agent 不输出可执行代码，只输出界面描述 JSON；客户端维护受信任的组件目录，只渲染目录里有的组件，用自己的原生组件实现，不执行 Agent 生成的任意 HTML。就像顾客只能点菜单上的菜，不能进厨房。
</details>

<details>
<summary>6. 动态生成软件时，为什么要把权限检查下移到数据层？</summary>

应用层代码随时被 Agent 生成或改写，可能漏掉一项权限检查、暴露不该看的字段或绕开已有判断，无论是生成错误还是被注入。权限检查若也在动态代码里，就和被约束的代码处在同一个信任域。放到稳定、经人审查的数据层（行级安全、受控视图、受信任运行时绑定的访问上下文），即使 AI 写错代码，越权操作也会被拒绝；前提是所有数据访问都经过这一层。
</details>

## 复盘卡

> **元能力**：思维、规则、呈现、接口、界面、Agent 自身，由内向外。
> **思考工具**：LLM 形式化，求解器求解；翻译这一步仍会错；模型越强，脚手架越薄。
> **规则**：提示词讲道理，参数做 checklist，数据库真值守门；最后一道防线建在模型无法伪造的数据上。
> **多媒体**：提议者-审核者分工是为了上下文；有紧凑精确描述、要精确可验证的用代码。
> **界面**：只能点菜单上的菜；Artifact 让数据绕过 LLM；动态软件的权限下沉到数据层。
> **自举**：确定性检查打底、LLM 兜底长尾；基于范例生成，而不是从零。
