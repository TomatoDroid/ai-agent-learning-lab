## 拆解

### 流程：计划先于行动，验证贯穿始终

<div class="anim" data-anim="coding-flow">▶ 动画“Coding Agent 的流程：什么时候算做完”需要在课程网站中观看。</div>

| 阶段 | 要点 |
| --- | --- |
| 项目文档化 | 先读 `CLAUDE.md` / `AGENTS.md`（项目级的系统提示词，天然对 KV Cache 友好）；没有就先读代码补一份 |
| 需求澄清 | 简单需求直接做；复杂需求先调研、必要时问人 |
| 设计文档 | 审查几十行方案比审查几百行代码容易：这是人最高效的介入点 |
| 测试-修复 | 失败了不报告失败，而是定位、修改，直到通过 |
| 自我审查 | lint、审查子 Agent |
| 文档同步 | 过时的文档比没有文档更糟 |

真实的 Coding Agent 会**按需裁剪**：修一个已知 bug 不需要设计文档。但有一步不能省：**测试通过**才算做完。写完不跑测试就报告“任务完成”，是 Coding Agent 最常见的偷懒方式。

一个“AI-ready”的简单指标：**远程新人只靠代码仓库和文档，能不能独立开展工作**。Agent 读不到口头约定。

### 为什么 Coding 最成熟

| | 结果可自动验证 | 结果需人工验证 |
| --- | --- | --- |
| **目标明确** | 最佳区域：修复有测试用例的 bug | 吞吐量受限于人的审查速度 |
| **目标模糊** | 高效地跑偏 | 难以启动 |

不是因为代码模型特别强，而是软件工程几十年攒下的测试、类型检查、Linter、Git 天然构成了一套 Harness。四条可以迁移到任何 Agent 的原则：**约束优先于指导**（“做不了”胜过“建议别做”）、**验证要自动化**、**反馈越快越结构化越好**、**回退要可靠**。

约束管的不只是结果，还有**过程**：删库重建也能“修好”数据库故障，删光代码也能“修好”编译错误。所以 `rm -rf`、删生产数据、覆盖未读文件这类动作要专门检查（5.2 课的语义解析、4.3 课的 Sidecar）。

### 故障与错误恢复

<div class="anim" data-anim="failure-recovery">▶ 动画“故障恢复：先分类，再计数，每条路径都有上限”需要在课程网站中观看。</div>

| 层 | 典型故障 | 怎么办 |
| --- | --- | --- |
| API | 429 限流、过载、超时、输出被截断 | 可重试的静默重试（退避 + 抖动 + 尊重 Retry-After）；输出触顶先提上限，再让模型从断点接续；持续过载降级或换厂商 |
| 工具 | 幻觉调用、参数畸形、反复同错 | 不终止会话，把结构化错误变成模型输入；对“工具名 + 参数”算指纹，反复出现就拦下 |
| 上下文 | 溢出、压缩失败、调用缺少配对结果 | 注入前自动修复配对（产品模式用占位符，训练数据模式拒绝修复） |
| 控制流 | 死循环、死亡螺旋 | 错误路径禁用会再调模型的副作用；递归深度计数；全局轮数、预算、升级到人 |

三条贯穿始终的原则：

- **先分类**：值不值得重试？参数错误原样重试一万次也一样。
- **恢复期间不暴露中间态**：恢复成功，用户毫无感知；全部手段用尽才呈现错误，并附上试过什么。
- **每条恢复路径都有上限**，阈值来自生产数据：Claude Code 的压缩熔断是“连续 3 次”，因为曾有会话在这条路径上连续失败三千多次。

还有一类故障不报错：流式连接**静默卡死**。SDK 的超时往往只管建连，所以需要独立的空闲看门狗：每个长连接都需要活性信号。

### 跨厂商接管

<div class="anim" data-anim="provider-handoff">▶ 动画“跨厂商接管：带走文字，丢掉凭证”需要在课程网站中观看。</div>

思考由两部分构成：可读的**文字**，和厂商附上的**凭证**（证明这段思考出自它自己）。**带得走的是文字，带不走的是凭证。** 各家要求不一，所以方案按最严格的一端设计：

| 做法 | 结果 |
| --- | --- |
| 直传 | 新厂商不认旧凭证，接口报错 |
| 一刀切剥光 | 接口可能通过（也可能不通过），但新模型不知道前情，重复调用 |
| 中立格式 | 凭证丢弃，文字作为普通内容带入，工具调用 id 重新生成；接收端强制要求凭证时，把历史调用改写成文字叙述 |

更一般的原则：**轨迹不按任何一家的接口格式存储**，而是存成中立格式。第七章的评估重放、第八章的训练样本、第九章的经验提取都依赖这同一份产物。

## 检验（先闭卷回答，再展开）

<details>
<summary>1. Coding Agent 的“完成”标准是什么？为什么要这么定？</summary>

测试通过，而不是代码写完。这是 Loop 工程“由验证判定何时可以停”在编码场景的落地。没有这个标准，模型最常见的偷懒就是写完不跑测试直接报告完成。
</details>

<details>
<summary>2. 为什么说 Coding Agent 成熟，功劳主要不在模型？</summary>

编码任务天然落在“目标明确 + 结果可自动验证”的象限：测试套件给出验收标准，Linter 和类型检查给出即时反馈，Git 提供回退。软件工程几十年积累的基础设施本身就是一套强大的 Harness。
</details>

<details>
<summary>3. 收到 429 和收到 400，处理有什么不同？</summary>

429 是可重试的基础设施噪声：指数退避加抖动后静默重试，尊重 Retry-After，用户无感知。400 是参数错误，原样重试多少次结果都一样，应立即抛出（或作为结构化错误交给模型改输入），不浪费配额。
</details>

<details>
<summary>4. 什么是死亡螺旋？怎么防？</summary>

错误处理路径里的逻辑本身又调用 LLM，再次出错，引发连锁反应。例如上下文溢出触发“结束时自动提交”的钩子，钩子调用 LLM 生成提交信息，再次溢出。防护：错误路径上禁用一切会再次调用模型的副作用，用递归深度计数器打断残余连锁，再加全局的轮数、预算和升级条件。
</details>

<details>
<summary>5. 跨厂商接管时，为什么“把思考删干净”不是万全之策？</summary>

一方面新模型失去了前情，容易重复调用工具；另一方面有的厂商强制要求凭证，凭证还可能附在工具调用上，删干净反而通不过校验。应该按最严格的一端设计：丢弃凭证，文字作为普通内容带入，id 重新生成；必要时把历史调用改写成文字叙述。
</details>

<details>
<summary>6. 为什么修复调用配对时，产品模式和训练模式要用不同的标准？</summary>

产品模式下用占位符补上缺失的结果，能让会话继续跑；但合成的占位符会污染训练数据，所以收集训练数据时拒绝修复。“产品模式宽容、训练模式严格”体现了 Harness 与模型训练的耦合。
</details>

## 复盘卡

> **流程**：文档化 → 澄清 → 设计（人审）→ 实现 → 测试-修复 → 自审 → 文档同步；按需裁剪，但完成标准永远是测试通过。
> **Harness**：约束优先于指导；验证自动化；反馈快且结构化；回退可靠；约束动作，不只约束结果。
> **恢复**：先分类再重试；检测指纹与连续失败；静默 → 降级 → 交给人；恢复期间不暴露中间态；每条路径都有熔断上限；错误路径不再调模型。
> **接管**：带走文字，丢掉凭证，id 重新生成；轨迹存中立格式。
