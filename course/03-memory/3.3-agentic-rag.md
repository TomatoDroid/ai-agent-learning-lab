## 拆解

### 把案例直接放进知识库，为什么不够

<div class="anim" data-anim="summary-index">▶ 动画“把案例直接放进知识库，为什么不够？”需要在课程网站中观看。</div>

两个案例暴露了三重障碍：top-k 只取回一部分（样本不全）；**最近邻偏置**（“护士”离“医生”最近）；**边界语义缺失**（“仅限……其他一律不适用”不存在于任何单条记录）。模型还没有“完整性信号”，不知道自己没看全，于是自信作答。

解法都在**索引阶段**：多花计算，把 100 个个案压成统计摘要，把散落的个案提炼成带边界的规则卡。这和 2.4 课状态栏的道理一样：把需要推理才能得到的结论，提前变成可检索的知识。

### 组织知识的几种方式

| 方式 | 结构 | 擅长 | 代价与局限 |
| --- | --- | --- | --- |
| RAPTOR | 自下而上聚类、逐层摘要成树 | 从概念逐步钻进细节 | 索引时多次 LLM 调用 |
| GraphRAG | 实体—关系图、社区摘要 | 多跳关系、实体消歧 | 三元组丢失条件和时间（语义降级），提取错误会污染知识 |
| 文件系统范式 | 目录 + L0 摘要 / L1 概览 / L2 全文 | 人可读可改、可进 Git、按需加载 | **文件之间必须有链接和索引**，否则会退化成孤岛 |

判断标准：查询主要是“找到包含某信息的片段”，混合检索就够了；经常需要跨文档综合或多层次导航，结构化索引才值得投入。推荐的折中是**分层互补**：自然语言保存核心信息，结构化元数据辅助索引，图谱只在医疗、法律、家族关系这类垂直场景作为专项索引。

### 知识如何更新：把知识库当代码库

| 层 | 内容 | 规则 |
| --- | --- | --- |
| 原始证据层 | 对话、轨迹、原始文档 | 只增不改 |
| 知识层 | 提炼后的 Markdown 或代码 | 每次修改是一个 PR |
| 服务层 | 检索索引 | 从已合入的版本重建，是可重建的派生物 |

**增量更新**：Proposer Agent 在分支上提交最小 diff → Reviewer Agent 回到原始证据独立审核 → 迭代至收敛（有上限，超限转人工）→ CI 检查后合入、重建受影响的索引。两者都必须是能搜索、比较、运行检查的 **Agent**，而不是两次固定的 API 调用；最好用**能力相近、家族不同**的模型，降低在同一处犯同类错误的概率。

**定期整理**：去重去旧、回到原始数据核查（不能只在摘要之间互相改写）、冲突解决与**场景限定**（两种说法可能分别在不同条件下成立）。

还有两条生产必备：**失效内容**用版本和生效/失效时间在检索阶段过滤；**权限过滤要下推到检索层**，越权内容一旦进入上下文，就很难保证不泄露。

### 智能体化 RAG：检索是工具

<div class="anim" data-anim="agentic-rag">▶ 动画“非智能体化 RAG vs 智能体化 RAG”需要在课程网站中观看。</div>

传统 RAG 是被动管道：检索一次、拼进上下文、生成。智能体化 RAG 把检索变成工具，模型按 ReAct 循环决定搜什么、搜几次、信息够不够。实验 3-8 的结论值得记住：简单问题两者质量相当，传统 RAG 更快；复杂的多跳问题，智能体化 RAG 明显更好。

**RAG 的安全边界**：检索到的文档是间接提示注入的典型载体，知识库投毒是同一回事。两层防御和第二章、第一章完全对应：来源标记（数据不是指令）；检索内容不能直接触发高风险操作。

### 上下文感知检索与双层记忆

<div class="anim" data-anim="contextual-retrieval">▶ 动画“上下文感知检索：给每个块补上‘身份’”需要在课程网站中观看。</div>

索引前，让 LLM 读全文和这一块，生成一句背景前缀，拼在块前再索引。它同时增强了 BM25（多了可精确匹配的词）和稠密检索（多了语义背景）。注意和第二章的“上下文感知压缩”区分：一个在索引期给知识库的块**做加法**，一个在运行期给对话历史**做减法**。

本章的两条线索在这里汇合成**双层记忆架构**：

- **概览层**：Advanced JSON Cards，少量关键事实常驻上下文；
- **细节层**：上下文感知检索，按需从海量原始对话里取回。

只靠常驻会丢细节，只靠检索会缺全局视野。主动服务（发现机票日期和护照有效期冲突）需要两者兼备。

### 从数据中发现知识

有些领域的知识藏在大量结构化案例里（判例、病例）。实验 3-12 的做法分两步：用 LLM 把案例转成统一 schema 的 JSON（schema 自下而上从样本中发现）；再用聚类等方法找出“案件原型”和因子重要性，让 Agent 按重要性追问、按原型给出有统计依据的回答。这是从“信息检索”走向“知识发现”。

## 检验（先闭卷回答，再展开）

<details>
<summary>1. 黑猫白猫的问题，调大 top-k 能解决吗？Xfinity 的问题呢？</summary>

黑猫白猫可以部分缓解，但成本随数据量增长，而且模型仍不知道自己是否看全。Xfinity 不能：“仅限……其他一律不适用”这种边界不存在于任何单条工单，取回再多也找不到。两者的解法都是在索引阶段提炼出摘要或规则卡。
</details>

<details>
<summary>2. 把“如果下周还下雨，我就取消海边计划改去博物馆”存成三元组，会丢掉什么？</summary>

条件（如果下雨）和时间依赖（下周）。三元组只剩下孤立的事实片段，比如“有计划：海滩旅行”和“有备选计划：博物馆”。这就是语义降级，也是不推荐把知识图谱作为通用记忆存储的原因。
</details>

<details>
<summary>3. Reviewer 和 Proposer 用同一个模型、只看 Proposer 挑选的片段，会出什么问题？</summary>

两者容易在同一处犯同类错误，Reviewer 只是沿着 Proposer 的结论再讲一遍；只看挑选过的片段，就发现不了被遗漏或被曲解的证据。应当用能力相近、家族不同的模型，让 Reviewer 能独立查询完整的原始证据，并且在权限上分工：Proposer 只能写分支，Reviewer 只读证据，只有合并流程能更新主库和索引。（原书思考题 9。）
</details>

<details>
<summary>4. 为什么权限过滤要放在检索层，而不是让模型“别说出来”？</summary>

越权内容一旦进入上下文，就很难保证它不以某种形式出现在回答里，提示词约束只能降低概率。在检索层过滤，越权内容根本进不了上下文。这和第一章“数据层护栏”的思路一致。
</details>

<details>
<summary>5. 上下文感知检索为什么能同时提升稀疏和稠密检索？成本怎么控制？</summary>

前缀给 BM25 带来了可以精确匹配的词（公司名、年份），给向量带来了语义背景。成本在索引阶段：每个块一次 LLM 调用。由于每次调用前面都是同一份全文，可以命中 Prompt Cache，书中估算约每百万文档 token 1 美元。
</details>

<details>
<summary>6. 双层记忆架构的两层各解决什么问题？</summary>

概览层（Advanced JSON Cards 常驻上下文）提供全局视野，让 Agent 知道有哪些关键事实、能发现跨会话的关联；细节层（上下文感知检索）按需取回原始对话的细节，用于核实。主动服务需要两者同时具备。
</details>

## 复盘卡

> **原则**：原始知识要在索引阶段提炼、抽象、结构化；把需要推理的结论变成可检索的知识。
> **工程**：证据只增不改，知识走 PR，索引可重建；失效和权限在检索层过滤。
> **检索**：检索是工具，由 Agent 决定搜几次；检索结果是数据，不是指令；概览常驻、细节按需。
