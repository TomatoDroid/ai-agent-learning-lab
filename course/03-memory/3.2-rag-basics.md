## 拆解

### 一条 RAG 流水线

```text
离线：文档 → 分块 → 索引（稠密向量 + 倒排索引）
在线：查询 → 并行检索（稠密 / 稀疏）→ 融合（RRF）→ 重排序 → 拼进上下文 → 生成
```

**分块**是第一道工序，原因有二：一整篇文档压成一个向量，多个主题混在一起，哪个都表达不准；检索的目标是只把相关的部分放进上下文。常用起点是每块 256–1024 token、重叠 10%–20%，然后按检索质量实测调整。生产系统最常用的是**递归/结构感知切分**（先按标题、段落切，超长再降级到句子）。

### 稀疏检索：BM25

<div class="anim" data-anim="bm25">▶ 动画“BM25：稀有词更重要，重复有上限”需要在课程网站中观看。</div>

BM25 保留了 TF-IDF 的核心直觉（词在这篇文档里出现得多、在整个语料里出现得少，就更重要），又修了两个毛病：

| 参数 | 管什么 | 直觉 |
| --- | --- | --- |
| k1 | 词频饱和 | 出现 10 次不该是 5 次的两倍 |
| b | 长度归一化 | 长文档仅仅因为字多而得高分，不公平 |

原书的 IDF 写法 `ln((N − df + 0.5) / (df + 0.5))` 在词出现于超过半数文档时会变负，实现里要设下限。这个下限在**小语料**上会咬人：用户记忆可能只有几十条，一个词只要出现在一半记录里就等于没搜。Lucene 和 Elasticsearch 改用 `ln(1 + …)`，永远为正。mini-agent 两种都实现了，测试里会让你看到区别。

### 稠密检索与它的盲区

稠密嵌入把文本映射成向量，语义相近的向量方向接近，用**余弦相似度**比较（看方向、不看长度）。上下文感知模型（BERT、BGE-M3）让同一个词在不同语境下得到不同向量，解决了 Word2Vec 的一词多义问题。海量向量要靠 ANN 索引：ANNOY 构建快、省内存但不支持增量更新；HNSW 精度高、支持增量更新但更占内存。

### 混合检索：融合与重排序

<div class="anim" data-anim="hybrid">▶ 动画“混合检索：两路各有盲区，融合后都能找到”需要在课程网站中观看。</div>

| | 稠密 | 稀疏 |
| --- | --- | --- |
| 强项 | 同义、改写、跨语言 | 人名、型号、错误码、代码 |
| 盲区 | 漏掉精确关键词（HTTP-403） | 读不懂同义词（kitty / cat） |

**RRF** 只看名次：`得分 = Σ 1 / (k + 名次)`，k 常取 60。它绕开了“余弦 0～1、BM25 0～几十”的尺度问题，简单稳健。

**重排序**不是为了补救 RRF 丢掉的分数，而是换了一种更强的匹配方式：**双编码器**像猎头筛简历，查询和文档各自编码，快但浅；**跨编码器**像面试官深谈，把查询和文档拼在一起逐字比对，准但慢，所以只用在融合后的前 N 个候选上。

### 怎么知道检索变好了

| 指标 | 回答的问题 |
| --- | --- |
| recall@k（本书口径，严格说是命中率） | 该找的找到了吗？只要相关文档进了前 k，LLM 就有机会用它 |
| MRR | 找到得够不够靠前？ |
| nDCG | 整个排序列表的质量如何？ |

没有这些指标，调分块大小、换嵌入模型、加重排序都只是凭感觉。这是第七章“评估”的预演。

## 检验（先闭卷回答，再展开）

<details>
<summary>1. 块太大和太小分别会怎样？</summary>

太小：单块信息不完整，脱离上下文后语义模糊（“该公司收入增长了 3%”是哪家公司？）。太大：一个块混杂多个主题，向量被稀释，检索精度下降，命中后还会带进大量无关内容。
</details>

<details>
<summary>2. 实验 3-5 中，“蒸馏”在 doc_1 出现 3 次，“模型”出现 5 次，为什么“蒸馏”贡献更大？</summary>

“蒸馏”只出现在 2 篇文档里，比“模型”（3 篇）更稀有，IDF 更高（1.22 对 0.76）。而且 BM25 的词频是饱和的，5 次相对 3 次的优势被压缩了。所以 1.22 × 1.75 ≈ 2.15，大于 0.76 × 1.99 ≈ 1.52。
</details>

<details>
<summary>3. 为什么用 RRF 而不是把两路分数直接相加？</summary>

余弦相似度通常在 0 到 1 之间，BM25 可以是 0 到几十的任意值，尺度和分布完全不同，直接相加会让 BM25 主导。RRF 只用名次，不需要对齐分数。代价是丢掉了分数里的相关性强弱信息。
</details>

<details>
<summary>4. 跨编码器更准，为什么不直接用它做检索？</summary>

跨编码器要把查询和每个候选拼在一起跑一遍模型，无法预先计算文档向量。对百万级文档逐一打分太慢。所以先用双编码器和 BM25 快速召回，再用跨编码器精排前几十个。
</details>

<details>
<summary>5. 书里的 recall@k 和学术上的 recall@k 有什么不同？</summary>

书里的口径是命中率：前 k 个里有一篇相关文档就算命中。学术上的 recall@k 是前 k 个结果中相关文档数除以该查询全部相关文档数。一个查询有多篇相关文档时，两者不相等。跨来源比较数字时要留意口径。
</details>

## 复盘卡

> **流水线**：分块 → 稠密 / 稀疏并行检索 → RRF 融合 → 重排序 → 生成，用 recall@k、MRR 验收。
> **互补**：稠密懂语义、漏关键词；稀疏认字面、不懂同义。没有哪一种单独可靠。
> **细节**：BM25 = 稀有词加权 + 词频饱和 + 长度归一化；小语料要换 IDF 写法。
