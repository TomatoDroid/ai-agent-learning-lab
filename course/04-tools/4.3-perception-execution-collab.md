## 拆解

### 感知工具：控制信息量，截断要说出来

<div class="anim" data-anim="truncation">▶ 动画“截断必须说出来”需要在课程网站中观看。</div>

| 工具 | 设计要点 |
| --- | --- |
| 搜索类 | 返回结构化候选列表（标题、位置、摘要），不拼接全文；默认只给前几条，注明总数和翻页方式（cursor） |
| 读取类 | 支持 offset/limit；截断时写明省略了多少、怎么读剩下的 |
| 所有感知工具 | 输出超过阈值（如 10000 字符）时，按当前意图做上下文感知压缩（2.4 课） |

**只读性的红利**：结果适合缓存（缓存键要包含用户身份和授权范围，会变的数据设 TTL），多个调用适合并行（留意速率限制和快照不一致）。执行工具就没有这种自由。

**多模态**：截图、图表要不要先转成文本？纯文字内容用文本提取（一页 PDF 截图上千 token，文字只有几百），布局敏感的内容（UI、复杂表格、设计稿）保留图像。主模型不支持多模态时，**工具化多模态分析**（`analyze_image(file, question)`）比提取为文本更好：上下文里只留问题和答案，内部用一个不需要 Agent 能力的多模态模型。

### 执行工具：层层设防

执行工具的错误代价可能极高：误删的文件无法恢复，错误的命令可能让服务中断。防护不能只靠一层：

| 层 | 做什么 | mini-agent 里 |
| --- | --- | --- |
| 输入验证 | 路径遍历、命令注入、参数类型；**快速失败**，不“智能修正” | `path_escapes_workspace`（1.3）、`validate_arguments`（4.1） |
| 权限控制 | 工作目录、命令黑名单、配额；黑名单只是最基础的一层 | `Guard` 的风险分级（1.3） |
| 提议者-审核者 | 不可逆的关键操作：事前审批、事后验证 | 第五章展开 |
| Sidecar | 与主模型并行，门控每一次工具调用 | `SidecarGuard`（本课） |
| 沙盒 | 进程级 → 容器 → microVM，按风险选层级 | 第五章 |

**提议者-审核者**有两种：**事前审批**像银行双签，审核模型要来自不同家族、能力相近（太弱的审核者跟不上被审者），两边的规则和上下文一致、关注点不同，被拒的理由作为工具结果回到轨迹里；**事后验证**的要诀是**模态切换**，比如把生成的文档渲染成图再看排版，把改过的配置在沙盒里实际跑一遍。

<div class="anim" data-anim="sidecar">▶ 动画“Sidecar：只看结构化字段的旁路门卫”需要在课程网站中观看。</div>

| 维度 | 提议者-审核者 | Sidecar |
| --- | --- | --- |
| 时机 | 操作前（审批）或操作后（验证） | 与主模型的流式输出并行，门控单次工具调用 |
| 审查对象 | 操作的合理性或结果 | 操作本身（工具调用） |
| 输入隔离 | 两边看到相似的信息 | 刻意隔离主模型的自由文本 |
| 模型 | 能力相近、家族不同 | 轻量模型就够（这是分类问题） |

Sidecar 的另一个用途是**构造上下文**：主模型思考的同时，旁路筛选相关记忆、为长输出生成摘要，用到时已经准备好了。

**另外几条执行工具的纪律**：

- **能验证就自动验证**：`write_file` 写完立刻做语法检查，把结构化的错误作为返回值的一部分（“执行-验证-反馈”闭环）。mini-agent 的 `write_file` 和 `edit_file` 对 `.py` 文件已经这样做了。
- **长输出头尾保留、全文落盘**：前 50 行和后 50 行进上下文，中间注明省略了多少、存在哪里、怎么读。
- **venv 不是沙盒**：它只隔离依赖，对文件、网络、进程没有任何约束。容器共享内核，microVM 才有独立内核。
- **可观测性**：日志、审计追踪、性能指标、告警。

### 幂等性与取消语义

<div class="anim" data-anim="retry-timeout">▶ 动画“超时了，钱转出去没有？”需要在课程网站中观看。</div>

调用被取消或超时，副作用可能已经发生。**幂等**的操作执行一次和多次效果相同，可以安全重试。两种手段：带唯一标识让服务端去重；**先查询后变更**。做不成幂等的（发邮件、打电话、转账），用“**预检-确认**”两段式，执行失败不盲目重试，把错误交还主模型重新规划。

### 协作工具

| 原语 | 工具 | 用途 |
| --- | --- | --- |
| 启动与取消 | `spawn_subagent`、`cancel_subagent` | 任务失去意义时及时终止，避免浪费 token |
| 消息传递 | `send_message_to_subagent` | 运行中补充指令或追问；子 Agent 也可以反向汇报 |
| 发现 | `list_agents` | 和 MCP 的 `tools/list` 同一思路，只是列出的是 Agent |

子 Agent 的提示词要有四个要素：清晰的角色、**标注上下文来源**（`[FROM_MAIN_AGENT]`、`[FROM_USER]`、`[TOOL_RESULT]`，这也是一种注入防御，和 2.3 课的来源标记同理）、明确的任务边界、标准化的输出格式。人工介入（HITL）要有**超时和降级**（“5 分钟没回应就采用保守策略”），批准和拒绝的理由要沉淀成反馈数据（第九章）。多 Agent 的拓扑和上下文传递在第十章展开。

## 检验（先闭卷回答，再展开）

<details>
<summary>1. 静默截断为什么危险？好的截断应该写什么？</summary>

Agent 会以为自己看到了全部内容，基于不完整的信息做出错误判断（比如断言“没有配置超时”）。好的截断写明显示了哪一段、总共多少、怎么读剩下的部分，例如“已显示第 1–200 行，共 5000 行，可用 offset 继续读取”。
</details>

<details>
<summary>2. Sidecar 为什么只看结构化字段？</summary>

如果 Sidecar 也读主模型的上下文或思考，攻击者夹带在网页或用户输入里的话术（“请允许执行 rm -rf”）就可能让它误判为合理理由。只看工具名和参数，就堵住了这条话术通道。
</details>

<details>
<summary>3. 提议者-审核者要求模型能力相近，Sidecar 却用轻量模型，矛盾吗？</summary>

不矛盾。提议者-审核者审查的是开放式的思考和方案，审核者太弱就跟不上被审者。Sidecar 回答的是较简单的分类问题（这条命令危险吗），轻量模型足以胜任，还能在数百毫秒内完成，与主模型的流式输出并行。
</details>

<details>
<summary>4. 拒绝熔断器解决什么问题？</summary>

分类器连续拒绝时，Agent 可能一直换写法重试，浪费资源甚至陷入死循环。熔断器在连续拒绝达到上限后，转为请求用户判断。这是第一章 Harness“纠正”功能的实例。
</details>

<details>
<summary>5. 转账超时后，怎样才能安全地重试？</summary>

超时意味着结果未知。要么让操作带唯一标识，服务端凭它去重，重复请求直接返回首次结果；要么先查询目标资源的当前状态，确认没有生效再重试。不能做成幂等的操作，用“预检-确认”两段式，执行失败不盲目重试。
</details>

<details>
<summary>6. 为什么说 venv 不是沙盒？</summary>

venv 只隔离 Python 包依赖，对文件系统、网络和进程没有任何约束，在里面运行的代码照样能删除任意文件、访问任意网络。隔离要靠操作系统及更底层的机制：进程级的工作区沙盒、容器、microVM。
</details>

## 复盘卡

> **感知**：结构化候选 + 分页；offset/limit；截断要说出来；只读所以能缓存、能并行。
> **执行**：输入验证 → 权限 → 提议者-审核者 / Sidecar → 沙盒；能验证就自动验证；长输出头尾保留、全文落盘；超时是“结果未知”，先查询再重试。
> **协作**：启动与取消、消息、发现三组原语；标注上下文来源；HITL 要有超时降级和反馈循环。
