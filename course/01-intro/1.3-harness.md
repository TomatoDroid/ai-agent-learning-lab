## 拆解

### Agent = Model + Harness

> **Harness = 上下文管理 + 工具接口 + 约束 + 验证 + 纠正**

| 职责 | 核心原则 | 例子 |
| --- | --- | --- |
| 上下文 | 信息要充分 | 系统提示词、知识库、状态栏 |
| 工具接口 | 接口要清晰 | MCP 工具、代码解释器 |
| **约束** | 故障安全默认值：所有能力默认关闭，必须显式开放 | Claude Code 中工具默认需要授权 |
| **验证** | 只看结构化数据，不看模型自由生成的文本（后者可能已被注入操纵） | Linter、类型系统、结果校验 |
| **纠正** | 确认无法恢复之前不暴露中间态 | 静默重试、熔断、回退到人工 |

两个关键判断：

- **成熟度不对称**：早期框架关注上下文和工具（“能做事”），生产系统的重心转向约束、验证、纠正（“可靠地做事”）。Claude Code 的 Harness 里，工具本身只占一小部分。
- **Harness 会被模型“吃掉”，但节奏很慢**：实验 1-4 展示了文生图的“提示词改写”节点如何被原生多模态模型内化。作者的立场是“方向认同，节奏务实”：模型还做不稳的，Harness 先补上；模型每内化一层，Harness 就卸下一层。

### 编排模式：工作流 vs 自主

<div class="anim" data-anim="orchestration">▶ 动画“订机票：工作流 vs 自主 Agent”需要在课程网站中观看。</div>

选择顺序：**先优化单次 LLM 调用，再考虑工作流，最后才引入自主 Agent**。Agent 系统用延迟和成本换取任务表现，要谨慎权衡这笔交换。

书中有一个很有用的反例：为“从百万条聊天记录中提炼个人记忆”画出一条有七八个专门 Agent 的流水线。每个部件单看都合理，组合起来却低效又脆弱，因为固定拓扑遇到新例外只能继续加节点。Manus 的说法是 **“Less structure, more intelligence.”**：程序只固化必须始终成立的边界（权限、不得覆盖原始材料、原子发布），边界内的决策还给模型。

### 三层护栏

<div class="anim" data-anim="guardrails">▶ 动画“三层护栏”需要在课程网站中观看。</div>

| 层 | 管什么 | 机制 | 局限 |
| --- | --- | --- | --- |
| 上下文层 | 模型能看到什么 | 相关性/安全分类器、内容审核、规则过滤、来源标注 | 同一个上下文里的 Agent 很难判断自己是否已被注入，只能降低概率 |
| 执行层 | 模型能做什么 | 工具风险评级、**上下文之外**的复核（独立审查、最小权限、沙盒、人在回路）、输出检查 | 依赖风险评级是否准确 |
| 数据层 | 世界最终能被改成什么样 | 行级安全、约束校验、不可伪造的访问上下文 | 需要在数据系统里提前设计好 |

越往下越不依赖模型自己的判断，所以越难被一次成功的攻击穿透。还要记住护栏的另一类失败：**误拒绝**。评估护栏时，既要测“该拦的拦住了吗”，也要测“该放的放行了吗”。

**人工干预**的两个触发条件：超过失败阈值；高风险操作。

## 动手：给 mini-agent 装上执行层护栏

这一课的练习实现的是本章思考题 7 的一个答案：**同一个工具，参数不同，风险也不同**。

打开 `mini-agent/mini_agent/guard.py`：

- **练习 1.3a**：`assess_risk`（动态风险评估）、`Guard.check`（高风险必须经 `confirm` 同意）、`Guard.record`（熔断器）。
- **练习 1.3b**：回到 `loop.py` 的 `_execute`，把护栏接进循环：被拒绝的调用不执行，返回 `DENIED: …` 给模型；执行结果计入熔断器。`run_agent` 里“熔断后停止”的逻辑在 1.2 已经写好。

```sh
python -m pytest tests/test_ch01_guard.py -v
```

做的时候想清楚三个设计决定，它们都来自本章：

1. **未知工具按 high 处理**：故障安全默认值。
2. **`confirm` 的默认值是“拒绝一切”**：所有能力默认关闭，必须显式开放。
3. **确认发生在模型上下文之外**：`confirm` 是一个 Python 回调（终端里问人，或交给独立的审查进程），模型无法通过生成文字来“说服”它。

完成后可以跑 `python -m mini_agent chat`（需要 API Key），让模型删一个工作目录外的文件，看看终端会不会拦下来问你。

## 检验（先闭卷回答，再展开）

<details>
<summary>1. 写出 Harness 的五个职责，并说明“验证”为什么只看结构化数据。</summary>

上下文管理、工具接口、约束、验证、纠正。验证只看工具返回的结构化字段等可信数据，因为模型自由生成的文本可能已经被提示注入操纵，拿它来做安全检查等于让被告自己判案。
</details>

<details>
<summary>2. 订机票客服：工作流还是自主 Agent？</summary>

可以混合：付款、出票这类有严格合规要求、顺序必须锁死的环节用工作流；理解需求、搜索比价、处理改签和意外用自主 Agent。工作流保证“付款前不能预订”这类规则不依赖模型判断，也把注入的影响限制在单个节点；自主部分提供应对未覆盖情况的灵活性。
</details>

<details>
<summary>3. 一段注入文字让 Agent 决定把文件发到外部邮箱。哪一层最可能拦住它？为什么不能只靠上下文层？</summary>

执行层：发邮件是高风险操作，需要上下文之外的复核（人工确认或独立审查）。上下文层只能降低概率，因为处在同一上下文里的 Agent 很难判断自己是否已被注入。如果执行层也失手，数据层的权限策略还能兜底。
</details>

<details>
<summary>4. LangChain 在 Terminal Bench 2.0 上从 52.8% 提升到 66.5%，改了什么？</summary>

没换模型，改的是 Harness：让 Agent 自动检查执行结果、检测是否陷入重复循环、优化思考策略等。这是“竞争优势转移到模型之外的工程实践”的例证。
</details>

<details>
<summary>5. 提示工程、上下文工程、Harness 工程、Loop 工程、Graph 工程是什么关系？</summary>

层层包含：提示工程 ⊂ 上下文工程 ⊂ Harness 工程 ⊂ Loop 工程 ⊂ Graph 工程。每一层都在前一层的基础上扩大了工程师的关注范围，单个 Agent 循环是执行图中的一个节点。
</details>

## 复盘卡

> **原则**：Agent = Model + Harness；生产级的差距在约束、验证、纠正。
> **边界**：Harness 很重要 ≠ 越复杂越好；程序守住边界，边界内交给模型。
> **安全**：上下文层降低概率，执行层和数据层给出保证；还要测误拒绝。
