## 拆解

### 轨迹是怎么长出来的

<div class="anim" data-anim="react-trace">▶ 动画“ReAct：轨迹如何一步步长出来”需要在课程网站中观看。</div>

一句话：**Agent 的上下文 = 静态前缀 + 轨迹**。每次调用模型，框架都把系统提示词、工具定义和截至目前的全部轨迹送进去；模型回一条消息，追加到轨迹里；如果其中有工具调用，框架执行后把结果也追加进去，然后再调用一次。

动画最后一步揭示了这个设计的代价：每轮都要重读全部历史，**累计读入量随轮数近似二次方增长**。这个问题第二章会用 KV Cache 回答，也是本章思考题 2。

### 分工：模型决策，框架执行

| 谁 | 做什么 |
| --- | --- |
| Model | 决定下一步：回答，还是调用哪个工具、传什么参数 |
| Harness | 组装上下文、校验并执行工具、把结果追加回去、判断何时停止 |
| Environment | 产生真实的状态变化和观察 |

实验 1-2 和 1-3 的对比值得记住：两者都是“模型决定何时调用哪个工具”，但在 Kimi 路径里，“调用模型 → 追加工具结果 → 再次调用”的循环仍由**客户端代码**驱动；在 Responses API 路径里，搜索、代码执行和多轮编排在**服务端**闭环完成。编排循环没有消失，只是位置变了。

### 停止条件

自主 Agent 必须有明确的停止条件，否则容易陷入死循环。常见的退出条件：

1. 模型返回了**没有任何工具调用**的回复（最常见）；
2. 调用了专门的“最终输出”工具；
3. 达到最大轮数；
4. 遇到不可恢复的错误。

然后运行检查点：

```sh
python -m pytest tests/test_ch01_loop.py -v
```

测试检查的每一条，都是原书的一条原则：

| 测试 | 对应原则 |
| --- | --- |
| `API无状态_每次调用都送回完整历史且只追加` | 模型 API 无状态；轨迹只增不改（第二章会说明这对缓存的意义） |
| `执行工具并把结果送回模型` | 工具结果是闭环控制的关键（实验 1-1） |
| `并行调用按顺序追加且id一一对应` | `tool_call_id` 把结果和调用对上号 |
| `未知工具变成错误观察而不是崩溃` | 错误也是观察；Harness 负责纠正，而不是把异常抛给用户 |
| `达到最大轮数时停止` | 停止条件 |
| `每次调用模型前执行before_call钩子` | 为第二章预留：状态栏、压缩都在调用前对上下文做处理 |

全部通过后，运行 `python -m mini_agent demo`，对照动画看一遍真实的轨迹。现在你可以回答 0.2 课的问题了：为什么每次调用读入的消息条数是 `[2, 6, 8]`？

<details>
<summary>答案</summary>

第 1 次：system + user = 2 条。第 1 轮追加 1 条 assistant（3 个工具调用）和 3 条 tool 结果，第 2 次就是 6 条。第 2 轮追加 1 条 assistant 和 1 条 tool，第 3 次是 8 条。
</details>

**接真实模型（可选）**：配好环境变量后运行 `python -m mini_agent chat`，问它一个需要换算货币的问题，观察真实模型会不会并行调用工具。

## 检验（先闭卷回答，再展开）

<details>
<summary>1. 写出 ReAct 循环的最小伪代码（不超过 10 行）。</summary>

```text
messages = [system, user]
repeat up to max_iterations:
    reply = model(messages, tools)
    messages.append(reply)
    if reply has no tool_calls: return reply.content
    for call in reply.tool_calls:
        result = execute(call)            # 出错也返回错误文本
        messages.append(tool(call.id, result))
return "max_iterations"
```
</details>

<details>
<summary>2. 为什么第二次请求要把第一次的 assistant 消息原样放回去？</summary>

API 是无状态的，模型不会“记住”上一次调用。把它自己之前的决策（包括工具调用）原样放回，模型才能看到自己做过什么；`tool` 消息也要靠这条 assistant 消息里的调用 id 才能对上号。
</details>

<details>
<summary>3. 工具抛出异常时，循环应该崩溃、跳过，还是把错误告诉模型？为什么？</summary>

把错误作为 tool 消息告诉模型。错误本身是环境给出的观察：模型看到“币种不支持”就可以换一种做法。直接崩溃会让 Agent 无法自我纠正；静默跳过则会让模型“盲目”，就像实验 1-1 里去掉工具结果一样。
</details>

<details>
<summary>4. Kimi 路径和 Responses API 路径的根本区别是什么？</summary>

两者都由模型决定何时调用哪个工具、工具都在服务端执行；区别在于 ReAct 循环跑在哪里：Kimi 路径的循环由客户端驱动，Responses API 路径整个编排闭环在服务端完成。
</details>

## 复盘卡

> **原则**：Agent 的上下文 = 静态前缀 + 轨迹；模型决策，框架执行，轨迹只追加。
> **边界**：循环必须有停止条件；错误要变成观察，而不是异常。
> **代价**：每轮重读全部历史，累计读入量近似二次增长。
